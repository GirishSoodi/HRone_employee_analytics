### Examined and Decided NOT a Defect

1. **Using PyMongo over an ORM/ODM:**
   Using direct PyMongo queries with Pydantic request models is appropriate and optimal for this project because it allows full control over exact aggregation pipelines (`$densify`, `$setWindowFields`, `$lookup`), avoids ORM overhead, and matches the contract's requirement that code reside in a clean single starter file.
2. **Naive UTC Datetime Handling in PyMongo:**
   PyMongo returns naive datetimes when retrieving BSON dates. Rather than modifying MongoDB driver defaults, standardizing on converting UTC naive datetimes to explicit UTC aware datetimes at the API boundary ensures predictable timezone math while keeping stored BSON datetimes standard.
3. **Absence of `ABSENT` / `LEAVE` creation in punch endpoints:**
   The starter punch endpoints only handle presence statuses (`PRESENT`, `WFH`, `ON_DUTY`). This is intentional as per contract section "Status values" (no endpoint creates ABSENT or LEAVE records; they come from seeded back-office data or manual regularizations).
